## Core claim

**Code has become cheaper to produce than to perceive.** AI-assisted development decouples two processes that used to be coupled: _production_ (characters appear, tests get written, systems change) and _absorption_ (mental models form, edge cases become intuitive, architectural relationships solidify). Production accelerates with the tooling. Absorption stays bounded by human processing speed. The gap is **cognitive debt**.

Unlike technical debt, cognitive debt is invisible to velocity metrics. Code works, tests pass, features ship — but the deficit lives in engineers' minds and only surfaces in lagging indicators (MTTR, Change Failure Rate), separated from velocity reporting by months.

## Three failure modes Pagade identifies

1. **The legacy heuristic inverts.** Engineers trust code that has survived in production for years — long-lived code is presumably correct. AI-generated code reverses this: **the longer it remains untouched, the more dangerous it becomes**, because the people-context that surrounded it has dispersed. Code barely understood when written becomes entirely opaque after authors move on.

2. **Debugging black boxes at 3 AM.** On-call engineers debug systems they didn't build, generated by tools they didn't supervise, with documentation that assumes familiarity they lack.

> They are debugging a black box written by a black box.

3. **The senior pipeline never forms.** Junior engineers who lean on AI-assisted dev never accumulate the implementation scar tissue that becomes architectural judgement. The organization trades next-quarter feature velocity for the future Staff Engineers who simply never form.

> The organization is effectively trading its pipeline of future Staff Engineers for this quarter's feature delivery.

## The reviewer's dilemma

AI inverts the rate-limiting step of code review. Juniors now generate code faster than seniors can deeply audit it. Reviewers face an impossible choice: maintain depth and become a bottleneck negating velocity gains; or rubber-stamp at arrival rate and hope tests catch what review missed. Most choose the latter, often unconsciously, because organizational pressure favours throughput.

> The organizational assumption that reviewed code is understood code no longer holds.

## The measurement problem

The fundamental challenge: organizations cannot optimize for what they cannot measure. Velocity is measurable; comprehension is not.

> The system is optimizing correctly for what it measures. What it measures no longer captures what matters.

Until comprehension becomes legible to organizational decision systems, incentives favour velocity. Engineers prioritizing understanding will appear less productive than peers who don't.

## Caveats Pagade flags himself

- Some tasks genuinely are mechanical; the framing doesn't apply uniformly.
- Comprehension may not have been forming at adequate rates pre-AI either; the distribution may be shifting, not a new phenomenon.
- Tooling and documentation practices may evolve to close the gap — making the debt manageable rather than accumulative.
